## Proposed ratchets (with measured baselines)

All counts run today with `rg` on this tree; "prod" = `src/` excluding `__tests__/` and `*.test.ts`. House patterns: **frozen-count strict-equal** (silent-failure-growth-ratchet.test.ts style, both-direction) vs **zero+named-allowlist** (src-no-sketchy-code.test.ts style).

**R1 — debug-only-catch (class: silent pump death; 5 confirmed instances #4,8,9,10,11)**
- Pattern (multiline regex, prod): `catch \(\w+\) \{\n(\s*//[^\n]*\n)*\s*logger\.debug\(` — catch whose first non-comment statement is a debug log.
- **Measured baseline: 11**, in exactly 6 files: http-sse.ts ×3, stdio.ts ×2, base.ts ×2, bun-spawner.ts ×2, isolated-client.ts ×1, search-index-backend.ts ×1. Promise-form (`.catch(… .debug(`) measured **0** → that arm can be zero-tolerance immediately.
- House pattern: **frozen-count at 11** (drop to ~5 once findings #4/8/9/10/11 are upgraded to warn + exit-propagation; tighten then). Zero+allowlist doesn't fit: drainStderr deadlock guards (stdio, base), isolated-client stop(), and search-index-backend safeObserve (documented L5 M-12) are legitimately debug-level forever.
- FP risk: low — first-statement form misses debug-then-rethrow blocks by construction (those are fine). Misses catch blocks where debug isn't first; acceptable narrowness, matches house norm.

**R2 — non-abortable-sleep (class: ≤2 confirmed #6,22; idiom shared)**
- Pattern (prod): `new Promise\(\s*\(?(r|res|resolve)\w*\)?\s*=>\s*setTimeout\(`
- **Measured baseline: 5** — agent/retry.ts:260, agent/lsp-bridge.ts:335, runtime/worktree.ts:58, session-resource-registry/disk-adapter/file-lock.ts:225, apps/cli/attach/attach-client.ts:264. (Finder claimed ~9; real prod count is 5.)
- House pattern: **frozen-count at 5**, burn down #6/#22 to 3, then re-pin. New code must use the abort-aware sleep in src/agent/loop/sleep.ts (test message should name it).
- FP risk: file-lock's 1ms retry hop and attach-client's 10ms poll are harmless yields — frozen-count tolerates them without an allowlist file.

**R3 — catch→return-empty-literal (class: fail-open masking; 2 confirmed #12 pair)**
- Pattern (multiline, prod): `catch \{\n\s*return (\[\]|\{\}|""|0|false)\n\s*\}` — extends the existing silent-failure-growth-ratchet's null/undefined arm (form B) with a form C for empty-collection masking.
- **Measured baseline: 94 prod (97 incl. tests)**.
- House pattern: **frozen-count** as a third counted form in tests/unit/silent-failure-growth-ratchet.test.ts (the file's header already positions it as the catch-all complement). Zero+allowlist is infeasible at n=94 — most are benign probes (`exists`, availability checks); only growth is the enforceable signal.
- FP risk: probe predicates get frozen alongside real maskers; that's fine — the rule only blocks NEW ones, and the fix message can point to the `ok:false`/logger alternatives.

**R4 — String(e) text classification (evasion of the existing `e.message.includes` ban)**
- Pattern: `\.test\(String\((e|err|error)\)\)|String\((e|err|error)\)\.(includes|match)\(`
- **Measured baseline: 1** (src/agent/lsp-bridge.ts:332 — finding #23).
- House pattern: **zero-tolerance after fixing #23** (branch on `e instanceof LspRequestError && (e.code === -32801 || e.code === -32802)`), added to src-no-sketchy-code.test.ts next to the `.message.includes(` ban it currently evades. Zero fits because a correct typed form always exists. Only 1 instance, but it's a hole in an already-enforced ban, so it qualifies.
- FP risk: essentially none at this specificity.

**R5 — JSON.stringify through a truncating write (class: non-atomic persisted state; 5 confirmed #1,2,3,17,19)**
- Pattern (prod, line-level): `(writeFileSync|writeFile|Bun\.write)\([^\n]*JSON\.stringify` excluding lines containing `atomic|tmp`.
- **Measured baseline: 13** — includes confirmed sites migration/persist.ts ×3 and knobs/persist.ts:66, plus session-memory-auto, node-repl/state-store, idle-monitor, registry-surface, apps/agent trust file, and 4 bench/eval output writers.
- House pattern: **frozen-count at 13**, burn down by routing through `@/storage` writeFileAtomic (ADR-0398); bench/eval writers (batch/report, batch/observe, eval/generator, eval/meta) can stay in the frozen set — they're run artifacts, not user state.
- Honest limitation: this catches the inline-stringify shape only. Findings #1 (source text), #2 (`json` variable), #3 (`body` variable) are invisible to any line regex — they need the direct fixes plus R6. Don't let the ratchet's green imply the class is closed.

**R6 — registry-built-but-never-torn-down (finding #7; same shape as the known BudgetExhaustionPolicy reader-0 class)**
- Not a regex ratchet — a **wiring-proof reader-count test** (house precedent: "zero unwired" / reader-count guards): assert `rg '\.stopAll\('` over src/ (excluding side-agent definitions/types) returns ≥1 call site, anchored to the session-teardown chokepoint (cleanupFinishedSession in src/agent/loop/session-lifecycle.ts). **Measured today: 0 call sites** — the test is born RED and lands with the fix.

Not ratcheted despite finder proposals (measurements disagreed or n=1): floating `void` promises (prod count **99**, only 1 confirmed defect #13 — the ratchet file itself documents biome's noFloatingPromises as the right tool once the 2.4.15 crash is fixed; freezing 99 with one confirmed bug is a weak signal-to-noise trade); `JSON.parse as <T>` (prod count **24**, not ~45 as claimed; 1 confirmed instance #14 — fix is reusing the S19 zod validator, then reconsider); Date.now ID-minting (raw prod count **10** before the assignment filter; 0 confirmed findings this audit).

## Non-mechanizable classes (review-checklist items)

1. **Error-kind routing at auth/token boundaries** (#15, #16): whether a caught token-endpoint failure should map to auth vs rate_limit vs network is semantic — no syntax distinguishes the correct catch from the wrong one (chatgpt-oauth even preserves `cause`, so the finder's cause-loss AST rule would NOT have caught either confirmed instance). Checklist: any catch that assigns an LLMError/OAuth `kind` must branch on a typed statusCode; `invalid_grant`/401 is the only re-auth trigger.
2. **Replace-vs-merge on persisted maps** (#18): "writeConfig(currentBag)" is indistinguishable from a legitimate full rewrite without knowing ownership of the file's other keys. Fix the two knobs sites directly; checklist: any `write*Config` whose input doesn't start from a fresh read of the same path needs justification.
3. **Read-tail-then-rename residual races** (#20) and lock-coverage gaps (#3): which writes must be lock-gated is a per-subsystem invariant; enforce with targeted hellgate tests (the existing retention hellgate injects its append at the wrong point — before readAppendedTail — and should be extended), not pattern scans.
4. **ok-semantics false-greens** (#5): `ok: pkt.failure === null` is syntactically innocent; only domain knowledge ("nothing ran ≠ green") flags it. Checklist: every tool result with `ok:true` must be reachable only from a path where the underlying action actually executed.
5. **Unserialized fire-and-forget RMW** (#13): `void f()` is already counted in house ratchets; the *race* (no epoch token, no serialization) is judgment-only.

## Coverage gaps

- **Clean-end pump death has no catch at all**: every pump finding (#4,8,9,10) has a sibling silent path — the stream ends WITHOUT throwing while the child/connection lives — which no catch-pattern ratchet can ever see. The real invariant is "pump settled while process/connection alive ⇒ fireExit/failAllPending", enforceable only via per-transport hellgate tests (inject a stream that ends early, assert pending requests reject promptly, not via timeout).
- **toctou dimension shipped no ratchet proposal** (finder returned empty); R5 covers ~the inline-stringify slice only. The general class (read → transform → truncating write of a path another process appends to) needs the per-subsystem lock/atomic-write fixes plus hellgates, not a scan.
- **Variable-payload truncating writes** (#1,2,3) are invisible to R5's line regex; an AST rule ("call to fs writeFile/Bun.write where the file does not import writeFileAtomic") is feasible with ts-morph but was not baselined here (raw write-site count is 129; needs the import-graph filter to be meaningful).
- **knobs read-path wiring**: the moment `bootstrapKnobs` gains a production caller, finding #18 escalates P2→P1 by the verdict's own terms; worth a one-line note in the fix commit or a reader-count guard mirroring R6.
- **Floating-promise enforcement is parked on biome**: the ratchet file documents `nursery/noFloatingPromises` crashing biome 2.4.15 on this repo — re-evaluate at the next biome upgrade; until then statement-position `void` calls (99 prod) have no growth bound.

## Appendix: refuted findings (adversarial audit trail)

These LOOK like defects but survived scrutiny as deliberate/documented/unreachable — do NOT re-report in future audits without new evidence:

- `src/plugin-isolation/bun-spawner.ts:277` [ignored-bound-catch] — Refuted on checks (2) and (3). The catch at src/plugin-isolation/bun-spawner.ts:275-282 is a documented, deliberate best-effort degrade: the port contract in src/plugin-isolation/types.ts explicitly states send() is "NO-THROW... Silently dropped if the child has exited", and the file-header comment (line 26-27 of types.ts) documents the exact recovery path the finder claims is missing: "send after exit: silently dropped (caller's request will time out at the host layer instead — a hard throw mid-send is worse than a typed timeout)". That host layer exists and is real: the sole production consumer (src/mcp/isolated-client.ts) wraps every send in a per-request JSON-RPC timeout (default 30s), so a dropped outbound message surfaces as a typed timeout error, not an invisible loss. The "unverified attribution" point is also weak: the log includes the actual error via errMessage(e), so misattribution loses nothing; and in Bun, FileSink.write on a pipe does not throw on backpressure (it buffers/returns a count) and encoding is already complete before the write, so the realistic throw class is exactly closed/EPIPE — i.e. "child closed" is accurate. The debug-vs-warn asymmetry with lines 258/266 is intentional severity routing: encode-fail and over-cap indicate caller bugs (warn), while write-after-close is an expected shutdown race (debug, to avoid teardown log spam). At absolute worst this is a log-message wording nit, not a prod-unsafe silent failure.
