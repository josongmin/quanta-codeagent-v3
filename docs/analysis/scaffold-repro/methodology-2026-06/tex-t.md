## 0. TEX-T 방법론 전부 펼치기 (근거 발췌 + 출처)

TEX의 알고리즘은 "한 라운드에 K개 에이전트를 병렬로 뽑고, 각자 (code patch C, test script T) 쌍을
낸다. 그다음 **모든 C를 모든 T에 실행**(cross-validation grid)하고, 각 에이전트에게 '내 C·T가 다른
모든 T·C에 대해 어떻게 나왔나'라는 peer 실행결과를 돌려주고, 다음 라운드로 계속 샘플링한다"이다.

### (a) N개 에이전트가 각자 code patch C + test script T 생성

> **verbatim (startuphub writeup):** *"Multiple agents work in parallel, each generating both a code patch (C) and a test script (T)."*
> **verbatim (WebSearch 요약):** *"At each round, K agents are sampled in parallel and each agent outputs a test file and code patch."*

핵심은 한 에이전트가 **동시에** fix(C)와 test(T)를 낸다는 것. code와 test가 커플링된 페어다.

### (b) Cross-validation 격자 — 모든 Cᵢ × 모든 Tⱼ 실행

> **verbatim (startuphub writeup):** *"every agent's code patch against every other agent's generated test script"* 로 피드백을 받는다.
> **verbatim (WebSearch, 2번째 쿼리):** *"TEX implements cross-candidate execution feedback where every agent's code patch is executed against the test scripts generated by all other candidates in the ensemble, and the results of this 'peer validation' are fed back to the agents."*
> **verbatim (WebSearch, 1번째 쿼리):** *"cross-validation is performed by running all generated code patches against generated test files. Each agent is provided with the execution result of running its code & test against all other tests & code."*

즉 K×K 실행 격자(각 candidate의 C를 다른 모든 candidate의 T로 검증). 이게 TEX의 이름값
("Execution-based Cross-Validation")이자 **진짜 lever**다.

### (c) Peer 실행결과를 다음 라운드 피드백 (self-only는 정체, cross가 핵심)

> **verbatim (startuphub writeup):** *"TEX solves this tradeoff by implementing cross-candidate execution feedback as the aggregation strategy."*
> **verbatim (startuphub writeup):** *"agents that only receive feedback from their own generated tests quickly stagnate."*
> **verbatim (startuphub writeup):** *"cross-candidate execution feedback continually improves performance over rounds."*

이게 논문의 중심 주장: self-only feedback(자기 T로 자기 C만 검증)은 **금방 정체(stagnate)**하고,
cross-candidate(남의 T로 내 C 검증) feedback만이 **라운드를 거듭할수록 계속 향상**한다.

### (d) 여러 라운드 반복

> **verbatim (WebSearch):** *"continues sampling in the next round"* / *"continually improves performance over rounds"*.

라운드 수 K의 정확한 숫자는 세 소스 어디에도 **명시 안 됨** [tag: 미측정 — blog 403이라 확인 불가].
"over rounds"라는 정성 표현만 확인. peer 결과를 프롬프트에 주입 → 다음 라운드 재샘플.

### (e) Random pass@1 선택 (앙상블 품질 충분하면 selector 불필요)

> **verbatim (startuphub writeup):** *"the quality of the generated tests and code is so high that random selection from the ensemble is sufficient for top performance."*

별도 학습된 selector/reranker 불필요. 앙상블 자체가 좋아서 **random pick으로 pass@1**을 낸다.
이건 우리 acceptance/LLM-rerank 철학과 정반대 방향(우리는 selector를 강화하는 쪽).

## 2. 핵심 판정 — cross-candidate execution feedback를 우리가 가졌나?

**결론: 안 가졌다. 우리 reprovote/acceptance는 TEX lever의 부분집합이 아니라 다른 축이다.**

TEX의 진짜 lever는 (b)+(c)의 **N×N 실행 격자 + peer 결과의 다음-라운드 재주입**이다. 축을 분해하면:

- **우리 reprovote** (`vote.ts:49` `voteResolved`, `repair/repro-vote.ts` K-of-N)는
  **N개 test script를 1개 patched tree(단일 fix)에 투표**한다. 목적은 "brittle 단일 script denoise"
  (`vote.ts:11-17`). 이건 TEX 축으로 보면 **"T 다양성으로 하나의 C를 검증"** — TEX의 T축 절반만,
  그것도 **cross 없이**. TEX는 여기에 **C 다양성**(여러 fix)을 곱하고 **모든 C×모든 T**를 돌린다. 우리엔 C축 격자가 통째로 없음.

- **우리 acceptance** (`acceptance-select.ts:174`)는 후보들을 **score-once + patch-vote + rerank**로
  **고른다**(selection). TEX는 (e)에서 "고르기(selection)는 random으로 충분"이라 하고 lever를
  selection이 아니라 **generation을 cross-feedback으로 끌어올리는 것**에 둔다. 즉 우리 acceptance는
  TEX가 "불필요하다"고 명시한 selector 정교화에 투자하고 있고, TEX가 "핵심"이라 한 cross-execution
  feedback loop는 비어 있다. **다른 축, 반대 우선순위.**

- **우리 repair-breadth** (`repair-breadth.ts`)가 구조적으로 가장 가깝지만 결정적으로 다르다:
  각 fork는 **자기 트리에서 자기 오라클로만** 검증(`:291` "candidate's own tree"),
  winner만 adopt하고 losers는 버리며(`:313`), peer 결과가 다음 라운드에 **안 흐른다**.
  이건 TEX가 명시적으로 "quickly stagnate"한다고 지목한 **self-only feedback 모드 그 자체**다.

**따라서 우리가 가진 것과 TEX의 관계:**
우리 = {N-fanout 생성} + {self-only 검증} + {강한 selector}.
TEX  = {N-fanout 생성 with (C,T) 페어} + {N×N cross 검증} + {peer feedback 재주입} + {random selector}.
겹치는 건 "N-fanout 생성"뿐. TEX의 이름값이자 성능근거인 **cross-candidate execution feedback loop는
우리에게 부재**이며, 우리 acceptance/reprovote는 그 부분집합이 아니라 **직교하는(그리고 TEX가 열등하다
판정한 self-only + selector) 축**이다.

**흡수 시 최소 델타(구현 지점, measure-first):** repair-breadth의 fork 팬아웃(`repair-breadth.ts:168`)에
이미 pool이 다 모이므로(`:137` OBSERVE-ONLY 전체 pool capture 존재), 여기에 (1) 각 후보가 repro-gen을
페어로 내게 커플, (2) `voteResolved`를 1-tree가 아니라 **pool의 모든 tree × 모든 script 격자**로 확장,
(3) 격자 결과를 다음 라운드 seed 프롬프트에 주입하면 TEX loop가 된다. C축 격자 + peer 재주입 2개가 핵심 갭.
단 §4 게임성(W1 monkey-patch/W2 soft-oracle) 때문에 `no-answer-key`·`claim-100-adversarial` 원칙상
"실 코드경로 호출 증명 + 구체값 단언" 가드 선결, default-OFF knob → SWE f2p로 A/B (SWT 점수 추격은 비추, 선행 리뷰 §6-B).
