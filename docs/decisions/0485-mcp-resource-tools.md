# ADR-0485: MCP resource/prompt tools (N3) — model-callable `resources/*` + `prompts/*` over a duck-typed port

- **상태**: Accepted
- **날짜**: 2026-06-06
- **관련**:
  - H19 (LANDED) — the `McpClient` `resources/list|read` + `prompts/list|get` methods this tool layer sits ON. H19 surfaced the typed no-throw client methods (INTERNAL — the agent loop could not call them); N3 is the agent-callable tool layer over them.
  - ADR-0471 (untrusted-source result envelope — the H2 `<untrusted-source>` envelope that wraps `mcp`-origin output at the dispatch seam; N3's whole security posture is "register through the `mcp`-origin array and inherit this", with no extra wiring)
  - ADR-0007 (MCP slice — the `@/mcp` slice that owns the concrete `McpResourcesPort` / `Mcp*` shapes this slice mirrors duck-typed)
  - ADR-0431 (MCP tasks live binding — the sibling `@/tool/mcp_tasks` slice this one mirrors structurally: duck-typed port + no-throw factory tools + composition-root bind)
- **참조**:
  - `src/tool/mcp_resources/port.ts` — duck-typed `ResourcesHandle` (4 NO-THROW methods returning `HandleResult<T>`) + the `Mcp*` mirror shapes (`ResourceEntry` / `ResourceBlock` / `PromptEntry` / `PromptMessage` / `PromptResult`) + closed `ResourcesFailureReason` union.
  - `src/tool/mcp_resources/render.ts` — PURE render + failure-map helpers: `truncate` (`MAX_OUTPUT = 50_000`), `mapFailure` / `renderFailure`, the NO-THROW `callPort` boundary, `renderResourceList` / `renderResourceContent` / `renderPromptList` / `renderPromptResult`.
  - `src/tool/mcp_resources/list_resources.ts` / `read_resource.ts` / `list_prompts.ts` / `get_prompt.ts` — the 4 `(port: ResourcesHandle) => Tool` factories.
  - `src/tool/mcp_resources/index.ts` — `mcpResourcesTools(port): Tool[]` (stable order: list_resources → read_resource → list_prompts → get_prompt).
  - `src/tool/index.ts` — `DefaultToolPorts.mcpResources?: ResourcesHandle` + the gated registration (`if (ports.mcpResources !== undefined) base.push(...mcpResourcesTools(...))`).
  - `src/tool/surface/manifest.ts` — N3 manifest row: `gate: { kind: "config-slot", slot: "DefaultToolPorts.mcpResources", env: "QUANTA_MCP_RESOURCES" }`, `default: opt-in` everywhere, `risk: "network"`.
  - Tests: `tests/unit/mcp-resource-tools-hellgate.test.ts` (39 cases), `tests/unit/composition-root-gated-port-activation-r3-hellgate.test.ts` (the deferred-bind contract).
  - Feature catalog: `tools/feature-catalog/features/09-integration/n3-mcp-resource-tools.yaml`.

## 맥락

MCP servers expose two read surfaces besides tools: **resources** (files / URIs the server makes readable via `resources/list` + `resources/read`) and **prompt templates** (named, argument-parameterized message templates via `prompts/list` + `prompts/get`). H19 (LANDED) gave quanta's `McpClient` the typed, no-throw `listResources` / `readResource` / `listPrompts` / `getPrompt` methods — but those are INTERNAL to the `@/mcp` slice. Before this ADR the agent loop could only reach `tools/list` + `tools/call`; the model could neither read a server-exposed resource nor materialize a server prompt template. H19 absorbed the client methods; this ADR (H19's agent-facing tool layer, RFC `jun-4-mcp-resource-tools`) closes the gap by exposing four model-callable tools.

Two constraints shape the design. First, the slice fence: `@/tool` may not import `@/mcp` (mirrors `@/tool/mcp_tasks`). Second, resource/prompt CONTENT is third-party, adversary-controllable DATA — a hostile or buggy MCP server can return megabytes of text, giant base64 blobs, or transcript-forging strings that try to forge an `<untrusted-source>` envelope close.

## 결정

**Four typed, read-only tools** over a single injected handle. Each factory is `(port: ResourcesHandle) => Tool`, all `isReadOnly() => true` + `isConcurrencySafe() => true`, and each `execute` is the identical shape: zod re-parse (fail-closed `ok:false` on bad input) → `ctx.signal.aborted` check (fail-closed `ok:false`) → ONE `callPort(() => port.method(...))` → a SINGLE `{ type: "result" }` event rendered through the pure helpers.

- `mcp_list_resources` (empty input) → `resources/list` → `renderResourceList`.
- `mcp_read_resource` (`{ uri }`) → `resources/read` → `renderResourceContent`.
- `mcp_list_prompts` (empty input) → `prompts/list` → `renderPromptList`.
- `mcp_get_prompt` (`{ name, arguments? }`) → `prompts/get` → `renderPromptResult` (args forwarded verbatim to the port).

**Port inversion (the fence).** The four tools speak to a duck-typed `ResourcesHandle` defined in `port.ts` — they NEVER import `@/mcp`. `ResourcesHandle` is a string-IDENTICAL mirror of `@/mcp/resources/port.ts`'s `McpResourcesPort` + `McpResult<T>` + `Mcp*` shapes (`McpResource` / `McpResourceContent` / `McpPrompt` / `McpPromptResult`). The composition root in the apps/host layer is the only place that adapts a concrete port (over a live `McpClient`) into this mirror; any drift between the producer shape and this mirror is a **TYPE error at the adapter site**, not a silent runtime mismatch. Every port method is documented NO-THROW: it returns a typed `HandleResult<T>` = `{ ok:true, value } | { ok:false, reason: ResourcesFailureReason, message }`, where `ResourcesFailureReason` is a CLOSED union (`unsupported | malformed | transport | too-large`) so the tool branches structurally instead of string-matching error text.

**The render layer (`render.ts`) is PURE + the untrusted-content firewall.** It maps the closed failure union onto a model-visible string + a typed `ToolFailure` (`unsupported` ⇒ `rejected`; the rest ⇒ operational `error` the loop survives). It owns three DoS guards, because the content is adversary-controllable: (1) all output is `truncate`-capped at `MAX_OUTPUT = 50_000` — the SAME value the sibling `list_tasks` tool uses (`list_tasks.ts:14`), not a threshold invented here, and the cap covers the FAILURE-message path too (a hostile `transport` error string is capped exactly like success content); (2) BLOB blocks are NEVER inlined — a base64 block emits a `[binary block … not inlined]` placeholder so the model knows binary content exists without flooding the transcript; (3) non-text prompt message `content` (the spec leaves it `unknown` — image / resource-block union) gets a typed `[non-text content block (kind) — not rendered]` placeholder, NOT a parse attempt (the block codec owner is the `@/mcp` source slice). `callPort` is the NO-THROW boundary: even though the port is documented no-throw, a buggy adapter that THROWS is collapsed to a typed `{ ok:false, reason:"transport" }` rather than rejecting the tool's async iterator (which would hang/corrupt the dispatch loop).

**No bespoke security wiring — provenance does it.** The render helpers deliberately do NOT re-implement defanging. Because these tools register through the `mcp`-origin array, `deriveProvenance(name, "mcp") === "mcp"`, so the H2/ADR-0471 `<untrusted-source>` envelope wraps + defangs their output at the dispatch seam. The slice's job is only to register through the right origin and cap size; the envelope is the security boundary.

**Default-OFF, gated activation.** Registration is conditional on `DefaultToolPorts.mcpResources` being wired (`src/tool/index.ts`): `if (ports.mcpResources !== undefined) base.push(...mcpResourcesTools(ports.mcpResources))`. Absent port ⇒ the four tools are NOT in `buildDefaultTools()` and the default menu is BYTE-IDENTICAL to the pre-N3 set — they are not part of `defaultTools`. The manifest gates them as `config-slot` / `QUANTA_MCP_RESOURCES`, `opt-in` on every surface, `risk: "network"` (each call is an outbound RPC and a resource read exfiltrates server data into the transcript).

## 결과

- The model can now enumerate + read a connected MCP server's resources and materialize its prompt templates — closing the "MCP client did tools-only" gap on top of H19's client methods.
- The `@/tool` → `@/mcp` fence stays clean: the slice is a leaf with a duck-typed port; the only `@/mcp` coupling is a type-checked adapter at the composition root.
- Untrusted MCP content cannot blow up memory/transcript (cap + blob placeholder + non-text placeholder) and cannot escape the `<untrusted-source>` envelope (mcp-origin ⇒ ADR-0471 defang) — both pinned by the 39-case hellgate.
- The composition-root bind is **deliberately deferred**: `agent-arg-builder` cannot reach a live resources-capable client (the bridge's `loadMcpTools` returns `McpStoppable`, which has no resources methods), so even with `QUANTA_MCP_RESOURCES=1` the production root does NOT register the tools today. `composition-root-gated-port-activation-r3-hellgate.test.ts` pins this as a documented gap (not an accidental default-on); the seam is proven live by passing a `ResourcesHandle` directly to `buildDefaultTools`. The host-side residual (a `clientResourcesPort`/`resourcesPortOver` adapter in `@/mcp` + a `resourcesToolsFor(client)` gate in `@/agent/mcp-bridge`) is the next wiring step.

## Trade-offs / Negative invariants

- **Port-inversion fence is a compile-time contract, not a runtime check.** `ResourcesHandle` must stay string-identical to `@/mcp/resources/port.ts`. Adding a field requires updating BOTH declarations; the safety net is that the apps-layer adapter assigns by identity, so any drift is a `tsc` error at the adapter site — there is no runtime reconciliation. The hellgate drives the tools over a hand-written FAKE handle, so it does not catch mirror drift; the type-check does.
- **Gated-activation byte-identity.** When `mcpResources` is unwired the default menu MUST be byte-identical to the pre-N3 set (`absent port ⇒ none of the N3 tools in the default menu`). The registration is purely additive and append-only in a fixed position; the hellgate pins both the absent case and the wired-case stable order (`list_resources → read_resource → list_prompts → get_prompt`). Any reordering or unconditional push is a regression.
- **Render safety bounds are load-bearing, mined from the hellgate.** (a) A giant text block is truncated to `MAX_OUTPUT + suffix` (no OOM). (b) A blob-only block emits a placeholder and the base64 is NOT present in the output. (c) A hostile `transport` failure message is capped on the FAILURE path (same bound as content) — a server cannot blow up the transcript through a giant error string. (d) Non-text prompt content yields a typed placeholder, never a throw. (e) `callPort` collapses a throwing port to `ok:false / transport`, never a false success and never an unhandled rejection. (f) Bad input + pre-start abort both fail closed to `ok:false`.
- **The envelope is the security boundary, not the render layer.** The render helpers MUST NOT re-implement defanging; they rely on the `mcp`-origin provenance ⇒ ADR-0471 envelope at dispatch. The critical hellgate invariant pins both halves: `deriveProvenance(name,"mcp")==="mcp"` for all four names, AND that a forged `</untrusted-source>` / re-opener in resource text is defanged (exactly one real opener + one real closer survive `wrapToolResult`). If a future change moves these tools off the `mcp`-origin array, the security property silently breaks — hence the provenance pin.
- **`risk: "network"` even though read-only.** Every call is an outbound RPC and a resource read exfiltrates server-side data into the transcript, so the manifest rates the group `network`, not `read`. `mcp_get_prompt` is read-only locally (a `prompts/get` only renders a template) but is still an outbound RPC.
- **Scope deliberately narrow.** `resources/subscribe` is a notification stream, not a request/response call, so it is NOT surfaced as a tool (Phase-2 deferred). Prompt-template materialization (injecting `get_prompt` output directly into context rather than as a tool result) is also deferred.
